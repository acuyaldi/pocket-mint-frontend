# Frontend Architecture — Pocket Mint

> Canonical owner of frontend architectural invariants: Next.js structure, auth, the API layer, state management, error handling, generated artifacts, Storybook, accessibility, and testing. Product visual rules live in `design.md` / `ui-system.skill.md`; this file owns everything else.

## Next.js Architecture

- App Router (`app/`), TypeScript throughout.
- Route groups: authenticated app screens live under `app/(app)/`; the
  layout for that group (`app/(app)/layout.tsx`) owns the authenticated
  shell (sidebar/topbar/navigation).
- Server Components by default. Add `"use client"` only where interactivity,
  hooks, or browser APIs require it — don't push it up to a whole page when
  a leaf component needs it.
- Providers (TanStack Query client, `next-intl`) are placed once at the
  root layout (`app/layout.tsx`), matching the same provider order
  Storybook's `preview.tsx` mirrors for stories.
- Route middleware is `proxy.ts` at the repo root, not `middleware.ts` —
  Next.js resolves it the same way; don't create a competing
  `middleware.ts`.

## Authentication

- Supabase is the source of truth for session/user identity.
- `proxy.ts` → `lib/supabase/middleware.ts` (`updateSession`) enforces
  **default-deny** routing: every route is protected unless explicitly
  allow-listed.
- Exact public allow list (as implemented): `/`, `/login`, `/changelog`,
  and anything under `/auth/`. Extend this list deliberately, not by
  exception-casing a new route elsewhere.
- Requests to protected backend endpoints carry the Supabase access token
  as `Authorization: Bearer <token>` — no API key, no client-supplied
  identity headers (`x-user-id` etc.); CI rejects those patterns (see
  Testing below).
- 401 handling is centralized in `lib/api.ts`'s response interceptor, not
  duplicated per-call-site.
- **Hidden UI is not authorization.** Conditionally rendering a link or
  button is not a security boundary — the route itself must enforce access
  via `proxy.ts` / `updateSession`.

## API Layer

- `lib/api.ts` is the single API abstraction (Axios instance + interceptors
  for auth attachment and 401 handling). All backend calls go through it.
- Never create a parallel `axios.create(...)`, a raw `fetch` wrapper, or a
  second HTTP client alongside it.
- New endpoints are added as functions/hooks that call the shared `api`
  instance, not as ad-hoc requests inside components.

## State Management

- TanStack Query (`@tanstack/react-query`) is the canonical async
  server-state layer — queries, mutations, cache invalidation.
- Do not introduce Redux, Zustand, Jotai, or another global state library
  unless the architecture intentionally changes (that's a decision for the
  user to make explicitly, not something to add opportunistically).
- Do not fetch data directly in a component's `useEffect` when a feature
  hook already exists (`src/features/*/hooks/`) or when one should be added
  there — colocate data access in hooks, not inline in components.

## Error Handling

- `lib/api-errors.ts` defines typed API-boundary errors
  (`AuthenticationRequiredError`, `AuthSessionError`). Reuse these; don't
  invent parallel error classes for the same conditions.
- Feature-level error helpers/components live alongside their feature under
  `src/features/`; reuse the existing pattern for a feature before adding a
  new one.
- Errors are surfaced to the UI as distinct error states — never rendered
  as empty or zero data (see `ui-system.skill.md` → Interaction and Data
  States).

## Generated Artifacts

- `next-env.d.ts` is committed and regenerated by Next.js tooling itself
  (currently pinned to `./.next/types/routes.d.ts`) — don't hand-edit it;
  if it drifts locally after running `next dev`, that's tooling output, not
  a change to make intentionally.
- `.next/`, `storybook-static/`, and Playwright artifacts
  (`playwright/.auth/`, `playwright/screenshots/`) are gitignored build
  output, not tracked source.
- Do not invent other "tracked generated artifact" conventions beyond what
  is actually committed in this repo.

## Storybook

- Config: `.storybook/main.ts`, `.storybook/preview.tsx`.
- `preview.tsx` wraps every story in the same provider order as the real
  app (`NextIntlClientProvider` → `QueryClientProvider`), plus a
  light/dark background toggle — keep story providers in sync with
  `app/layout.tsx` if that order ever changes.
- Two CI-enforced gates (`.github/workflows/ci.yml`):
  - **Storybook build** (`npm run build-storybook`) must succeed.
  - **Storybook Vitest project** (`npx vitest run --project=storybook`,
    defined in `vitest.config.ts`) runs every story as an accessibility +
    interaction test via `@storybook/addon-vitest` and Playwright Chromium.
- Storybook's `a11y` addon runs with `test: "error"` — an accessibility
  violation in any story **fails CI**, not just a lint warning.
- Repository convention (not independently CI-enforced beyond the above):
  colocate `*.stories.tsx` next to the component it documents
  (e.g. `components/ui/app-modal.stories.tsx`).

## Accessibility

Verified expectations only — this is not a WCAG-compliance claim:

- Every interactive element has an accessible name.
- 44px minimum touch targets.
- Keyboard operability and a visible focus indicator on every interactive
  element.
- Status/state is never color-only.
- Storybook's `a11y` addon (`test: "error"`) is the CI-enforced gate for
  story-covered components; anything not covered by a story isn't checked
  by that gate.

## Testing

- Vitest projects (`vitest.config.ts`): `unit` (Node environment,
  `tests/**/*.test.ts`) and `storybook` (browser environment via
  Playwright Chromium, running story files).
- `tests/` holds Node-environment unit/contract tests
  (e.g. API client behavior, page contracts, business-rule tests) — see
  existing files there for the established naming and structure before
  adding a new one.
- Playwright is used as the Storybook Vitest project's browser provider,
  not as a separate standalone E2E suite in this repo today.
- CI (`.github/workflows/ci.yml`) gates, in order: lint, typecheck,
  changelog contract test, full `unit` project, production build,
  Storybook build, `storybook` project, plus repo-specific scans (no
  tracked secrets, no legacy backend auth headers in source or bundle, no
  unexpected tracked-file drift after verification).
- Don't freeze or hardcode an expected test count anywhere — the suite
  grows; assert behavior, not size.

## Future Assistant Integration (architectural boundary only)

No Assistant frontend exists today. If one is ever built, it must:

- Reuse `lib/api.ts` — never a parallel API client.
- Reuse existing feature hooks rather than re-fetching data ad hoc.
- Reuse the existing authentication flow (Supabase session + `proxy.ts`).
- Reuse existing routing conventions (`app/(app)/` route groups).
- Preserve backend deterministic execution — the frontend never becomes a
  second source of financial truth (see `financial-logic.skill.md` →
  Future Assistant UI).

This section states boundaries only. Do not design Assistant UX here.
